# Command Reference

The GitGone CLI is organized into logical groups to help you manage your secrets, teams, and projects efficiently.

## Authentication & Config

<Accordions>
<Accordion title="gitgone login">
  Authenticate your CLI with your GitGone server. You will be prompted for your email and password directly in your terminal. Your password never leaves your machine: the CLI derives an authentication key from it.

  On a GitGone Cloud instance, the CLI opens your browser to sign in with your cloud account instead (use `--password` to force a password login). On a new self-hosted server that has no administrator yet, it creates the administrator account.

  Accounts created before this protocol are upgraded automatically on their next login.
</Accordion>
<Accordion title="gitgone activate">
  Activate an account created by an administrator. You enter the activation code you received, choose your password, and your encryption keys are generated on your machine.
</Accordion>
<Accordion title="gitgone passwd">
  Change your password. Your vault is re-encrypted locally and your other sessions are logged out.

  <Callout type="warn">
    Nobody can recover a lost password, not even an administrator. A reset (`gitgone admin users reset`) gives you a new account key, and team owners will have to share your projects again.
  </Callout>
</Accordion>
<Accordion title="gitgone config">
  Manage your local configuration (like the server URL).
  - `gitgone config set <key> <value>`
  - `gitgone config get <key>`
  - `gitgone config list`
</Accordion>
</Accordions>

## Working with Secrets

These are the commands you'll use most frequently during development.

<Accordions>
<Accordion title="gitgone init">
  Initialize GitGone in your current project directory. It creates a `.gitgone` configuration file.
</Accordion>
<Accordion title="gitgone link">
  Link your local directory to an existing project on the GitGone server. This is useful when you've cloned a repository that already uses GitGone.
</Accordion>
<Accordion title="gitgone push">
  Encrypt and upload your local `.env` file to the server for a specific environment.
  ```bash
  gitgone push
  ```
  Options:
  - `-e, --env <environment>`: Target environment (default: "development").
</Accordion>
<Accordion title="gitgone pull">
  Fetch and decrypt the latest secrets from the server into your local `.env` file.
  ```bash
  gitgone pull
  ```
  Options:
  - `-e, --env <environment>`: Target environment (default: "development").
</Accordion>
<Accordion title="gitgone run">
  Inject secrets directly into your application's memory without touching the disk. 
  **Recommended for security.**
  ```bash
  gitgone run -- npm start
  ```
  Options:
  - `-e, --env <environment>`: Target environment (default: "development").
</Accordion>
</Accordions>

## History & Rollbacks

<Accordions>
<Accordion title="gitgone history">
  List the version history of secrets for the current project and environment.
</Accordion>
<Accordion title="gitgone rollback">
  Revert to a previous version of your secrets instantly.
  ```bash
  gitgone rollback
  ```
</Accordion>
</Accordions>

## Project Tokens

Project tokens allow applications (like those in CI/CD pipelines, or programmatic scripts) to fetch secrets without a user account.

<Accordions>
<Accordion title="gitgone tokens list">
  List all active tokens for the current project. Legacy tokens (created before v2) are flagged and should be recreated.
</Accordion>
<Accordion title="gitgone tokens create <name>">
  Generate a new project token, in the form `v2.<id>.<secret>`. The secret is generated locally and never sent to the server: only a verifier derived from it is.
  
  <Callout type="warn">
    The token secret is only shown once. Make sure to save it securely!
  </Callout>

  Options:
  - `-e, --env <environment>`: The environment this token has access to.
</Accordion>
<Accordion title="gitgone tokens delete <id>">
  Revoke a project token by its ID.
</Accordion>
</Accordions>

## Team Management

Manage your collaboration units.

<Accordions>
<Accordion title="gitgone team create <name>">
  Create a new team (organization) on the server.
</Accordion>
<Accordion title="gitgone team list">
  List all teams you are a member of.
</Accordion>
<Accordion title="gitgone team list-members">
  List all members and their roles in a team.
</Accordion>
<Accordion title="gitgone team add-member">
  Invite a new member to your team by their email address.
</Accordion>
<Accordion title="gitgone team remove-member">
  Remove a member from a team you own. Their copies of the project keys are deleted, then the key of every project of the team is rotated, since they may still know the old ones.
</Accordion>
</Accordions>

## Project Management

Manage applications within your teams.

<Accordions>
<Accordion title="gitgone project create <name>">
  Create a new project within one of your teams.
</Accordion>
<Accordion title="gitgone project set-policy">
  Configure security rules for the current project:
  - **Standard**: Allows `gitgone pull` to disk.
  - **Memory-only**: Disables `pull`, forcing the use of `gitgone run` so secrets are never written to disk.

  <Callout type="info">
    This policy is a guardrail for well-behaved clients, not a security boundary: any member who can decrypt the secrets can still write them to disk.
  </Callout>
</Accordion>
<Accordion title="gitgone project rotate-key">
  Generate a new project key (owners only). The whole secrets history is re-encrypted with it on your machine, and the new key is shared with every current team member.

  <Callout type="warn">
    Project tokens are tied to the old key: they are revoked and must be recreated with `gitgone tokens create`.
  </Callout>
</Accordion>
</Accordions>

## Key Management

GitGone uses end-to-end encryption. These commands help manage the keys that protect your data.

<Accordions>
<Accordion title="gitgone keys share">
  When a new member joins a team, they don't have the project keys yet. An existing member with access must run this command to securely share the project key with them.
  
  <Callout type="info">
    This process is fully encrypted. Your CLI will fetch the new member's public key and encrypt the project key specifically for them.
  </Callout>

  The first time you share with someone, the CLI shows their key fingerprint and asks you to confirm it (compare it with theirs through another channel). The fingerprint is then pinned: if the server ever returns a different key for them, sharing is refused.
</Accordion>
<Accordion title="gitgone keys fingerprint">
  Display your public key fingerprint, so teammates can check it when they share a project with you.
</Accordion>
<Accordion title="gitgone keys forget <email>">
  Forget the pinned fingerprint of a user, after they legitimately got a new key (account reset). Check their new fingerprint with them before sharing again.
</Accordion>
</Accordions>

## Administration

Commands reserved for server administrators (SuperAdmins).

<Accordions>
<Accordion title="gitgone admin users">
  Manage users globally on the server.
  - `gitgone admin users list`: List all registered users.
  - `gitgone admin users create`: Invite a new user. It prints a one-time activation code (valid 72h) to send to the user, who then runs `gitgone activate`.
  - `gitgone admin users reset`: Reset a user who lost their password. Their keys and project access are wiped and a new activation code is issued.
</Accordion>

<Accordion title="gitgone admin teams">
  Manage teams globally on the server.
  - `gitgone admin teams create <name>`: Create a new team.
  - `gitgone admin teams list-members`: List members of any team.
  - `gitgone admin teams add-member`: Add any user to any team.
</Accordion>
</Accordions>

  You can always use the `--help` flag with any command to see more details and options:
  ```bash
  gitgone team --help
  ```
</Callout>
