title: Daily workflow

GitGone treats secrets a bit like code: everyone works from the same shared version, changes are pushed, and every version is kept. Without ever committing a secret to Git.

## The loop

<Steps>
<Step>
### Get the latest secrets

```bash
gitgone pull
```

Your `.env` is updated with the latest version of the environment of the folder. If it differs from yours, the CLI shows which variables would change before overwriting it.
</Step>

<Step>
### Change what you need

Edit `.env` as usual: add a key, change a URL. GitGone does not change your habits.
</Step>

<Step>
### Share it

```bash
gitgone push
```

The CLI lists the variables you added, changed or removed, then sends a new encrypted version. Your teammates get it with `gitgone pull`.
</Step>
</Steps>

<Callout type="info">
  Prefer not to keep a `.env` on disk? Run your app with `gitgone run -- npm start`: the secrets are passed to it directly. See [Run without a .env file](/docs/cli/guides/run-without-env).
</Callout>

## Environments

A project usually has `development`, `staging` and `production`. Each folder has a default environment, chosen with `gitgone init`. Use another one with `-e`:

```bash
gitgone pull -e staging
gitgone run -e production -- node server.js
```

Protect `production` so that only maintainers can push to it: see [Protect production](/docs/cli/guides/protect-production).

## When something goes wrong

- **A bad push?** Restore the previous version with `gitgone rollback`. See [Restore a previous version](/docs/cli/guides/restore-version).
- **Who changed it?** `gitgone history` lists the versions and their authors, `gitgone audit` every action.
- **Someone leaves?** Remove them: the keys they knew are rotated. See [Remove a teammate](/docs/cli/guides/remove-teammate).

## New teammates

A newcomer needs an account, a role, and the key. Then `gitgone init` and `gitgone pull` in the repository are enough. See [Onboard a teammate](/docs/cli/guides/onboard-teammate).
